# Admin-managed S3 Storage Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Configure S3 exclusively through the admin UI and use it for new document originals and versions, preserving authorized delivery of SQLite and S3 content.

**Architecture:** SQLite retains metadata and encrypted singleton settings. A storage service coordinates settings changes, writes original bytes to S3 and persists version references atomically with metadata. All delivery and PDF loaders read through the same content service; durable deletion jobs retry outside SQL transactions.

**Tech Stack:** Go >=1.26.1, Echo v4, modernc SQLite, AWS SDK for Go v2, AES-256-GCM; Svelte 5/SvelteKit, existing API client and Playwright.

**Spec:** `docs/superpowers/specs/2026-10-15-s3-storage-design.md`

## Global Constraints

- No S3 environment variables, AWS credential discovery, STS or instance metadata calls.
- Secrets never enter API responses, audit payloads or localStorage. Automatically generated `storage.key` uses 0600 and survives in the database volume.
- New migrations are idempotent; existing SQLite BLOBs remain readable. S3 versions store empty BLOBs and an atomic sidecar reference.
- New uploads use a stable configuration snapshot. Referenced bucket/endpoint/region/addressing cannot change; disabling retains existing S3 reads and cleanup.
- Production custom endpoints require HTTPS and TLS verification. SDK requests have bounded retries and deadlines.
- Connection probe uses Put/Get/Delete within 15 seconds. Ordinary object requests use 60 seconds, subject to caller cancellation.
- Original delivery remains behind JWT, RBAC, NDA and existing PDF authorization checks. Never issue public or presigned object URLs.
- UI copy is English. Existing upload limits, checksums, MIME sniffing and monotonic version numbering remain intact.
- Execute inline on the existing clean `work` branch in the managed workspace, as authorized by the user's “Делай”. Record task progress in `/tmp/s3-implementation/progress.md`.

## Review Focus

- Disabled S3 still serves its old objects; missing encryption key does not disable SQLite reads.
- Failed Put or failed SQL commit never advances a document pointer or silently stores a SQLite copy.
- Settings changes cannot race uploads or pending object cleanup into another endpoint.
- Deleting the last version never sends DeleteObject; failed physical cleanup survives restart.
- Unauthorized and view-only users never obtain original S3 bytes or storage metadata.

## File Structure

- `internal/domain/storage.go`: persisted configuration, safe settings view, object location and cleanup job data; document model adds a private storage reference.
- `internal/repository/migrations/006_s3_storage.sql`, `storage_repository.go`: settings and deletion outbox; document repository adds transactional storage reference insert/load/delete.
- `internal/service/storage/{secrets,s3,service,content,cleanup}.go`: credential cipher/key lifecycle; SDK transport; admin operations and synchronization; content lifecycle; retry worker.
- `internal/handler/storage_handler.go`: admin endpoints and sanitized errors; document handlers consume a narrow content interface.
- `cmd/main.go`: inject repository/service/content and start/cancel cleanup worker.
- `ui/src/routes/admin/storage/+page.svelte`, admin layout and API types: form, connection test, saved-key handling and short instructions.
- Repository/service/handler tests plus targeted Storage Playwright scenario: failure cases and end-to-end regression.
- README, CLAUDE.md, API/user/deployment docs: usage, object permissions, backup and operational limits.
