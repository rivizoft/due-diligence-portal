# S3 через админку: спецификация

Дата: 2026-10-15. Статус: согласовано пользователем; реализовано и проверено.

## Цель и критерий успеха

Администратор подключает AWS S3 или S3-совместимое хранилище через админку. После включения новые документы и новые версии загружаются в выбранный bucket. Настройки сохраняются после перезапуска, применяются без перезапуска и не требуют S3 env-переменных. Рядом с формой есть короткая инструкция.

Документы, загруженные до подключения, остаются доступны из SQLite. Скачивание, NDA, права доступа, водяные знаки и защищённый PDF-просмотр работают для обоих хранилищ.

## Контекст проекта

- Go 1.26.1, Echo v4, SQLite через modernc.org/sqlite; Svelte 5, SvelteKit, Carbon.
- `internal/handler/document_handler.go` загружает документы и версии в BLOB; `internal/repository/document_repository.go` сохраняет их транзакционно и распределяет номера версий.
- `internal/handler/document_delivery.go` проверяет права до чтения файла и повторно перед выдачей. PDF-сервис получает содержимое через отложенный callback после допуска задачи.
- SQLite использует одно соединение. Сетевые операции внутри SQL-транзакции недопустимы.
- `DB.Migrate()` выполняет все SQL-файлы при каждом запуске, поэтому новые миграции должны быть идемпотентными.
- Админка использует отдельные страницы `/admin/*` и существующий типизированный API-клиент.

## Выбранный подход и границы

S3 становится необязательным хранилищем оригиналов новых документов и версий. Метаданные, категории, права, аудит и номера версий остаются в SQLite. Один документ может содержать версии из разных хранилищ.

Используется одно подключение S3. Автоматический перенос старых BLOB, несколько одновременно настроенных подключений, прямые браузерные загрузки, публичные URL, отдельный файловый менеджер, multipart/resumable upload и настройка bucket из приложения не входят в эту задачу. Branding assets и вложения NDA продолжают использовать существующее хранение в SQLite.

Отключение S3 меняет только назначение новых загрузок на SQLite. Сохранённые настройки и ключи остаются доступны для чтения и удаления ранее загруженных S3-версий.

## Админка

Новая страница `/admin/storage`, пункт навигации `Storage`, заголовок `Storage Settings`. Текст интерфейса — на английском, как в существующей админке.

Поля:

| Поле | Поведение |
|---|---|
| `Use S3 for new uploads` | По умолчанию выключено. |
| `Bucket` | Обязательно для подключения; имя существующего приватного bucket. |
| `Region` | Обязательно; регион подписи запросов, например `eu-central-1`. |
| `Access Key ID` | Ввод нового ключа; сохранённое значение показывается только маской. |
| `Secret Access Key` | Password input; сохранённое значение никогда не возвращается. |
| `Endpoint URL` | Необязательно; пустое значение означает стандартный AWS endpoint. Пользовательский endpoint — абсолютный HTTPS URL без userinfo, query и fragment. |
| `Use path-style addressing` | Для S3-совместимых провайдеров; по умолчанию выключено. |
| `Key prefix` | Необязательно; например `documents/`. Нормализация завершающего `/`; запрет управляющих символов и сегментов `.`/`..`. |

Пустые поля ключей при редактировании означают «сохранить текущую пару». Для замены требуется ввести оба поля. Для первого подключения требуется новая пара. Backend различает отсутствие значения, пустое значение и новую пару; маска никогда не отправляется как ключ.

Кнопки `Test Connection` и `Save Settings` блокируются на время соответствующего запроса. Есть состояния загрузки, ошибок и успешного сохранения. Несохранённые поля проверяются именно в текущем виде. Проверка не включает S3 и не сохраняет настройки автоматически. Секрет очищается из состояния формы после успешного сохранения и не записывается в localStorage.

Короткая инструкция рядом с формой:

1. Create a private S3 bucket and keep public access blocked.
2. Create an access key with GetObject, PutObject and DeleteObject permissions for the selected bucket/prefix.
3. Enter the bucket, region and keys. For an S3-compatible provider, enter its HTTPS endpoint and enable path-style addressing if required.
4. Click Test Connection, enable S3 for new uploads, and save. Existing documents remain in their current storage.

Чтение и проверка подключения также доступны только администратору. UI поясняет, что отключение не удаляет файлы и что изменение bucket/endpoint после загрузок ограничено.

## API и проверка подключения

Все маршруты регистрируются на `adminGroup` с JWT и `RequireRole(admin)`:

- `GET /api/v1/storage`: безопасное представление настроек, `credentials_configured`, маска Access Key ID и признак блокировки местоположения. Секреты и шифротекст не входят в ответ.
- `PUT /api/v1/storage`: проверяет поля, объединяет их с сохранёнными ключами, проверяет подключение при включении или изменении параметров подключения, затем атомарно сохраняет настройки. Простое отключение не требует доступности S3. Неуспешная проверка сохраняет прежнее состояние.
- `POST /api/v1/storage/test`: принимает такие же поля, использует сохранённую пару только при пустых полях ключей, выполняет проверку без сохранения.

Проверка создаёт объект со случайным именем внутри настроенного префикса, читает его, проверяет точное совпадение байтов и удаляет. Успех означает, что проверены все три операции; HeadBucket и ListBucket не требуются. Для всей проверки установлен timeout 15 секунд. Удаление пробного объекта предпринимается и после промежуточной ошибки, с отдельным ограниченным контекстом.

Ответы следуют существующему response envelope: 400 для неверных полей, 403 для другой роли, 409 для запрещённого изменения местоположения, 503 для недоступности/отказа S3, 504 для timeout. Сообщение указывает этап проверки без ключей, подписанных URL, сырых XML-ответов и авторизационных заголовков.

## Хранение настроек и секретов

Новая singleton-таблица `storage_config` хранит enabled, bucket, region, endpoint, path-style, prefix, зашифрованную пару ключей и время обновления. Данные читаются сервером при выполнении операции; S3 credentials provider явно использует сохранённые ключи, без default credential chain и чтения AWS/S3 env-переменных.

Для шифрования используется AES-256-GCM из стандартной библиотеки Go: случайный nonce на каждую запись, версия формата и фиксированная associated data. Ключ шифрования автоматически генерируется при первом сохранении credentials и хранится в файле `storage.key` рядом с SQLite database, с правами 0600. Создание файла защищено от перезаписи, symlink и гонок; существующий ключ проверяется на длину и права. Тесты используют отдельный временный каталог и внедрённый ключ.

Ключ не зависит от JWT secret и не задаётся через env. При отсутствии/повреждении файла для существующего шифротекста сервер не создаёт новый ключ поверх старого состояния: S3-операции возвращают понятную ошибку, обычные SQLite-операции продолжают работать. Для стандартного `/data/portal.db` файл находится в `/data/storage.key` и переживает перезапуск контейнера в существующем volume.

В инструкции по backup фиксируется необходимость сохранять SQLite, `storage.key` и S3 objects. Шифрование защищает секреты при отдельной утечке SQLite; доступ к базе вместе с ключом позволяет расшифрование.

## Привязка версий и ограничения редактирования

Новая таблица `document_version_storage` содержит FK на `document_versions.id`, bucket и полный object key. Наличие строки означает S3; отсутствие означает SQLite. S3-версии сохраняют пустой BLOB `[]byte{}` для существующего `file_data BLOB NOT NULL`, а реальный размер и SHA-256 остаются в метаданных.

Sidecar-строка создаётся в той же транзакции, что документ/версия и указатель current_version. Старые миграции и BLOB не переписываются. Метаданные можно получить без чтения BLOB и обращения к S3.

Пока есть S3-версии, незавершённые S3-загрузки или задания удаления, изменение bucket, endpoint, region и path-style запрещается с 409. Замена пары ключей к тому же хранилищу разрешена после успешной проверки. Префикс можно менять: каждая версия уже содержит полный object key. Отключение не снимает запрет и не стирает ключи.

Операции изменения настроек и назначения места новых загрузок координируются серверным сервисом: запрос получает стабильный снимок конфигурации, а несовместимое изменение не может обогнать незавершённую загрузку. Приложение остаётся одним процессом на SQLite, как в существующем deployment.

## Загрузка и обработка ошибок

Используется AWS SDK for Go v2: явные credentials, region, endpoint и path-style; ограниченные retries, request context и TLS verification. Никакого обращения к instance metadata или STS.

Object key имеет вид `<prefix><document-id>/<version-id>`. Использование уникального version ID вместо номера версии предотвращает коллизии параллельных загрузок: номер по-прежнему выдаётся внутри SQLite-транзакции.

Backend сохраняет существующие ограничения размера, проверку ролей, определение MIME по байтам и SHA-256. Для S3 выполняется PutObject, затем транзакционно сохраняются метаданные и ссылка. Бинарные данные не дублируются в SQLite. Сетевой запрос не держит SQL-транзакцию.

Ошибка PutObject не создаёт документ или новую версию. Ошибка SQLite после PutObject инициирует удаление созданного объекта. При сбое компенсирующего удаления сохраняется задание на повторную очистку, если база доступна; сообщение и логи не раскрывают credentials. Автоматического fallback в SQLite при ошибке включённого S3 нет. При аварийном завершении между записью объекта и фиксацией SQLite возможен orphan object; полная распределённая атомарность и автоматическая сверка всего bucket не обещаются.

Существующий путь загрузки читает файл в память; в этой задаче не вводится отдельная потоковая или resumable архитектура. Timeout внешней операции — 60 секунд, включая ограниченные retries; отмена HTTP-запроса передаётся в SDK.

## Чтение и PDF

Единый сервис содержимого версий выбирает SQLite или S3 по сохранённой ссылке. Получение S3-объекта ограничивается ожидаемым размером плюс один байт и существующим лимитом размера; проверяются размер и SHA-256. Удалённый или повреждённый объект выдаёт контролируемую ошибку без выдачи неполных данных.

`document_delivery.go` использует этот сервис как для обычного скачивания, так и внутри PDF callback. Метаданные и проверки доступа выполняются до сетевого чтения, а повторная проверка доступа и существования версии остаётся перед выдачей. Сетевое чтение для PDF происходит только после допуска задачи, сохраняя ограничения workers/queue/input size.

Оригиналы хранятся приватно. Browser получает файл или PNG-страницы только через существующие backend endpoints. Временные URL S3 не выдаются; CORS bucket и изменения browser CSP не нужны. Branding, watermark и NDA правила остаются действующими.

Недоступный S3 не препятствует запуску приложения, логину, работе админки и чтению SQLite-документов. Запрос к недоступному S3 получает 503/504; отсутствие объекта или несовпадение checksum — контролируемую ошибку содержимого, без fallback на пустой BLOB.

## Архивирование, удаление и аудит

Архивирование сохраняет все оригиналы, как сейчас. Последнюю версию нельзя удалить; проверка остаётся транзакционной и выполняется до удаления S3-объекта.

При удалении S3-версии SQL-транзакция удаляет версию/ссылку, переключает current_version и добавляет durable-задание удаления объекта. После commit backend предпринимает удаление. Ограниченный фоновый worker повторяет неуспешные задания после рестарта с backoff; сетевые запросы выполняются вне SQL-транзакций, отсутствие объекта считается успехом. Такой порядок не оставляет доступную версию с уже удалённым объектом при сбое SQLite. UI сообщает успех логического удаления, физическая очистка может завершиться позднее.

Настройки и результаты проверки пишутся в аудит без request body и ключей. Существующие события загрузки, скачивания, просмотра и удаления сохраняются.

## Проверки и критерии приёмки

1. Repository: повторный запуск новой миграции; чтение старой базы; атомарность метаданных и S3-ссылки; отсутствие дублирующего BLOB; параллельное распределение номеров; запрет удаления последней версии; durable cleanup.
2. Encryption: расшифрование после повторного открытия ключа; разные nonce; отсутствие plaintext в DB/API; повреждение ciphertext/key; безопасное создание файла и сохранение после restart.
3. Admin API: admin-only для всех трёх endpoints; валидация; пустые ключи сохраняют пару; частичная замена отклоняется; тест не сохраняет; неуспешное включение не меняет прежнюю конфигурацию; отключение работает при недоступном S3.
4. S3 adapter: локальный HTTP test server через внедрённый transport для SDK; корректные bucket/key и подпись, path-style, последовательность test Put/Get/Delete, timeout/cancellation, ошибки чтения/удаления и размер/checksum. Production endpoint policy остаётся HTTPS.
5. Document integration: существующий SQLite upload/download; S3 initial upload и новая версия; смешанные версии; S3-read после отключения; запрет смены местоположения при references/jobs/in-flight upload; уборка после SQL failure; отложенное удаление и повтор после restart.
6. PDF/access regression: watermarked download, view-only PNG preview, права/NDA и повторная проверка после подготовки — для S3 и SQLite. Инвестор без прав не вызывает S3 GetObject и не получает bucket/key/credentials.
7. UI: наличие страницы и инструкции; первый ввод, проверка и сохранение; загрузка настроек после обновления страницы без секрета; поведение ошибок и отключения; навигация.
8. Финальная проверка: `go test ./... -count=1`, `go vet ./...`; в `ui` — `npm test`, `npm run check`, `npm run lint`, `npm run build`; целевые Playwright сценарии для Storage и document/PDF lifecycle с изолированными данными. Реальные облачные ключи не требуются для автоматических тестов.
